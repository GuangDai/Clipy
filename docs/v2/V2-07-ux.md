# V2-07 - UX Interactions (integration of V2-01..V2-06 UX surfaces)

> **Status (2026-07-26):** V2 design-consolidated, scaffold proof pending. This
> doc extends the v1 specification (`00`–`06`) by **addition only**. It is the UX
> **integration** of the V2 capabilities whose grafts are owned by V2-01..V2-06;
> it owns **no graft of its own** (no E1/R1-R3/J1/C1-C3/S1/X1-X2/P1-P3/M1). It
> redefines no v1 public type, `HistoryAction` case, schema column, codec,
> invariant (D1–D19, `02` §14), or proof gate. v1 UX behavior — main-actor SwiftUI
> views, observable presentation state, snapshot-replacement observation,
> accessibility, localization — is owned by `01` §6, `03b`, `04` §5, and `06` §1
> (state-3 acceptance, point 3); V2-07 owns only the **new** UX surface that
> consumes V2-01..V2-06 DTOs. Like v1
> and V2-01..V2-06 at consolidation time, V2-07 is "design-consolidated, scaffold
> proof pending."

## 1. Role and boundary

V2-07 answers one question:

> *How are the UX surfaces of the six V2 capability docs — enrichment status,
> retention settings, change-history/reconnect, transparent materialization caches,
> external-connection/audit management, and locale-aware search — integrated into
> the v1 PresentationUI/ClipyApp main-actor UI without weakening a single v1
> load-bearing decision, the v1 isolation model, the v1 snapshot-replacement
> observation contract, or D1–D19?*

V2-07 is **not a capability**. Its "evidence trigger" is the admission of at least
one user-facing V2 capability: it ships as those capabilities ship, and a V2
surface that no capability admitted is never built. It introduces **no new
graft**, **no new `HistoryAction` case**, **no new `HistoryMutation`/
`StampedMutation`/`PlannedOutcome` case**, **no new schema table/column**, **no
new codec**, **no new actor**, and **no new durable state**. Its entire material is
the V2-01..V2-06 public DTOs and protocols, composed on the main actor.

V2-07 owns:

- the **UX principles** for V2 surface (§3), inherited from v1 and made explicit
  for the V2 capability set;
- the **"not live-observed" pattern** and the **UI re-browse contract** (§4) — the
  central cross-cutting rule that governs how the UI reflects V2 config/derivation
  writes that advance no `ChangePosition`;
- the **per-capability UX surfaces** (§5), consolidated from the `§12`/`§13` UX
  hooks each part doc deferred to V2-07;
- the **settings consolidation** model (§6) — where V2 settings live and how they
  classify as `HistoryAction` vs distinct-concern protocol writes;
- the **code model** (§8) — main-actor `@Observable` presentation state, the
  protocol cast pattern in `ClipyApp`, the no-leakage boundary;
- the **accessibility + localization** contract (§9/§10) for V2 surface;
- the graft-admission protocol records (§11), V2 proof gates (§12), and the
  V2-self-review scan (§17).

### 1.1 What V2-07 is NOT

- **Not a new graft.** None of E1/R1-R3/J1/C1-C3/S1/X1-X2/P1-P3/M1 is owned here.
  Each V2 surface is the UX projection of a graft admitted in its owning doc.
- **Not a new public DTO owner (in the general case).** V2-07 introduces **no new
  public `HistoryCore` DTO** (§7). Every status/setting value the UI renders is a
  sibling-doc DTO (`EnrichmentStatus`, `ThumbnailCacheStatus`,
  `LocalizedSearchStatus`, `HistoryRetentionPolicies`, `ConnectionDTO`/`GrantDTO`/
  `OperationRecordDTO`, `ReconnectBatch`/`HistoryChangeRecord`/`JournalEntryKind`,
  the V2-02 receipt outcomes). The only new types V2-07 introduces are
  **PresentationUI-internal** main-actor `@Observable` view models and SwiftUI
  views — PresentationUI's own surface (`01` §2: "View state and interactions over
  History DTOs"), not `HistoryCore` public types, so they do not cross the target
  boundary and do not trigger `V2-00` §4 records 2/3/5 for a *new public DTO*.
- **Not a cache, not a security boundary, not a schema migration.** Records 4/5/6
  (§11) are correspondingly "not applicable / none / surfaces V2-05's only."
- **Not a redefinition of v1 UX.** v1 PresentationUI behavior (the history list,
  search, detail, pin/paste, thumbnail) is unchanged; V2-07 *adds* surface next to
  it. A v1 caller that ignores every V2 distinct-concern protocol sees the v1 UI.

### 1.2 What V2-07 explicitly lifts

V2-07 lifts **no v1 exclusion** and **no `06` §3 G-graft**. It is the consumer of
the lifts already recorded in V2-01..V2-06 (`V2-00` §3). It re-states, for UX, the
honest consequence of each capability's observation model — in particular, that
derivation/config writes that advance no `ChangePosition` are **not** reflected by
a live `observe(...)` until the next real History Commit or a fresh `browse`
(`V2-01` §4.1, `V2-04` §12, `V2-05` §13). This is stated here in one place rather
than re-argued per surface.

## 2. Capability scope

### 2.1 In scope (UX integration of admitted V2 capabilities)

- Main-actor SwiftUI views and `@Observable` presentation state, built only from
  `HistoryCore` DTOs (v1 + V2 sibling-doc DTOs), rendering the per-capability
  surfaces listed in §5.
- A consolidated V2 settings panel (§6) bound to the V2 distinct-concern protocols
  and the V2-02 `HistoryAction.setRetentionPolicies`.
- The UI re-browse contract (§4) that honestly reflects not-live-observed V2
  writes without claiming live freshness it cannot deliver.
- Accessibility labeling and localization for every new V2 status/indicator/
  control (§9/§10).

### 2.2 Out of scope (remains with the owning doc or post-V2)

- **Any new graft, public DTO, protocol, schema, codec, actor, or invariant.**
  These belong to V2-01..V2-06 (or post-V2). V2-07 consumes; it does not mint.
- **A live OCR-completion push notification.** `V2-01` §12 (amended) states there
  is **no** OCR-completion push - `EnrichmentHistory` (`V2-01` §8) exposes no
  observation stream - and the UI re-browses on the next History Commit / a fresh
  `browse(.search)`. V2-07 does **not** invent a push (it is V2-01's surface to
  own); V2-07's re-browse contract (§4.2) is authoritative. (OPEN-1, which
  escalated stale V2-01 §12 wording, is **resolved** - the wording was amended
  to match this contract; see §14.)
- **A live retained-storage-usage indicator.** V2-02 exposes the *budget*
  (`HistoryRetentionPolicies.storage.maxTotalBytes`) and the
  `.retentionPoliciesSet(retiredItems:prunedRevisions:)` receipt, but **no public
  current-retained-bytes read** — the byte summary is a planner-internal fact
  (`V2-02` §3.2 `RetentionExpansionItemSummary`). V2-07 does not invent a public
  read for it; a live usage indicator requires a V2-02 protocol extension, recorded
  as OPEN-2, not introduced here.
- **A "recently removed" / reconnect surface, unless product-approved.** V2-03's
  reconnect (`ReconnectHistory`) is a distinct-concern protocol; whether it is
  user-exposed is a product decision (`V2-03` §2.3 trigger (b)). V2-07 defines the
  DTO-consuming view shape (§5.3) but ships it only if that trigger fires.
- **Push-based audit-log updates.** `GatewayAdminHistory` admin operations advance
  no `ChangePosition` and yield no `HistoryInvalidation` (`V2-05` §13); the audit
  viewer re-reads on demand (§5.5), it does not subscribe to a live audit feed.
- **Multi-process / CloudKit / network UX.** Excluded for V2 (`V2-00` §3.1).

### 2.3 Evidence trigger (admit design work)

V2-07's evidence trigger is **the admission of at least one user-facing V2

## 3. UX principles (inherited from v1, non-negotiable)

These are v1's UX load-bearing rules (`01` §6, `03b`, `04` §5, `06` §1 point 3),
restated for the V2 surface. V2-07 adds **none**; it inherits all.

1. **Main-actor only.** SwiftUI views, observable presentation state, selection,
   and window behavior run on the main actor (`01` §6). No SwiftData context/row/
   model identity, no content fingerprinting, no rich-text parse, no image decode,
   no OCR, no PDF parsing, no audit-hash computation on the main actor. V2 adds no
   exception: V2-01 OCR/PDF (`V2-01` §6.2), V2-04 decode (`V2-04`), V2-05 grant
   checks (`V2-05` §5.1) all run on their own actors; the UI only receives
   `Sendable` DTOs.
2. **Built only from `HistoryCore` DTOs (+ new V2 DTOs).** The UI imports only
   `HistoryCore` (+ SwiftUI); it holds `any ClipboardHistory` and the V2
   distinct-concern protocols as injected `Sendable` references, never
   `SwiftDataHistory`'s concrete internals (`01` §4, §8; `V2-00` §6.6). No
   `@Model`/`ModelContext`/`PersistentIdentifier`/Domain state crosses into UI
   (`01` §6 boundary rule; `V2-00` §2.2).
3. **Observation is snapshot-replacement, not event deltas.** `observe(_:)`
   produces authoritative first pages followed by replacement pages after relevant
   History Commits (`04` §5). The UI keeps "the latest returned page" as ordinary
   caller state (`04` §11) and never applies event deltas. New V2 DTOs the UI
   observes follow the same model.
4. **Accessibility + localization (state-3 acceptance).** Every UI element is
   accessibility-labeled; every user-facing string is a `LocalizedStringResource`
   (`06` §1 point 3; §9/§10). The search-projection locale (P2, `V2-06`) is a
   **separate concern** from UI localization.
5. **No new public UX type that collides with v1.** V2-07 reuses v1 DTOs
   (`HistoryRow`, `HistoryDetails`, `SearchPresentation`, `PastePayload`,
   `HistoryPage`, `ThumbnailPayload`) where a capability extends them, and the
   sibling-doc V2 DTOs where it does not. It adds no name colliding with v1
   vocabulary (`V2-00` §9).
6. **No concrete platform claim without a citation or a proof gate.** SwiftUI
   availability, `@Observable`, `LocalizedStringResource`, and the accessibility
   modifiers are stated with their MCP-verified availability or assigned a V2 proof
   gate (§12), exactly as v1 (`00` §5).

## 4. The "not live-observed" pattern and the UI re-browse contract

This is the central cross-cutting UX rule V2 introduces. It is the honest
consequence of the V2 observation model already recorded in V2-01/V2-04/V2-05/V2-06;
V2-07 states it once, as a UI contract.

### 4.1 Why some V2 writes are not live-observed

v1's race-free observer wakes only on a `HistoryInvalidation` whose position is
**strictly greater than** the yielded page (`04` §5 steps 4 and 6: "position > P").
A `HistoryInvalidation` is yielded **only** by a non-empty History Commit, which is
the only thing that advances `ChangePosition` (`04` §4). Therefore any V2 write
that **advances no `ChangePosition`** yields **no** `HistoryInvalidation` and
cannot wake a live `observe(...)` without extending `04` §5's wake predicate — a
deeper internal-coherence change V2 deliberately does **not** take for
enrichment/cache/gateway/journal writes (`V2-01` §4.1, Record 2); the sole
exception is the P2 predicate-change signal (§4.3), which wakes `observe(.search)`
via a `HistoryInvalidation`-peer signal rather than by extending the position-keyed
wake predicate.

The V2 writes that advance no `ChangePosition` and are therefore **not
live-observed** are exactly the distinct-concern protocol config/derivation writes:

| Write | Owning protocol | Advances `ChangePosition`? | Live-observed? |
|---|---|---|---|
| `setEnrichmentEnabled` | `EnrichmentHistory` (`V2-01` §8) | no | no |
| `persistEnrichment` (OCR/PDF result) | (internal; `V2-01` §6.4) | no | no |
| `setDiskThumbnailCacheEnabled` / `setMaxDiskThumbnailCacheBytes` / `clearDiskThumbnailCache` | `ThumbnailCacheHistory` (`V2-04` §10) | no | no |
| `enrollConnection` / `revokeConnection` / `grantCapability` / `revokeCapability` / `rebaseAuditChain` | `GatewayAdminHistory` (`V2-05` §7.2) | no | no |
| journal config writes (cache toggle, retention window, compact-now) | (pending public `JournalAdminHistory`, OPEN-5; today internal `V2-03` §10.3) | no | no |
| `setLocalizedSearchEnabled` / `setLocalizedSearchLocale` | `LocalizedSearchHistory` (`V2-06` §4.5) | no | **yes — via the predicate-change self-heal (§4.3)** |

Contrast: the V2-02 retention writes **are** History Commits. `.setRetentionPolicies`
is a `HistoryAction` that retires/prunes and advances `ChangePosition` exactly once
(`V2-02` §4.5, D6). An active `observe(.recent)`/`observe(.search)` therefore
reflects V2-02 retirements via the standard v1 snapshot replacement — no special
UX handling. (R3 pruning of inactive revisions changes `HistoryDetails.revisions`
on the next `details(for:)` read; no live revision-list observation is added
(`V2-02` §12).)

### 4.2 The UI re-browse contract

For every not-live-observed V2 write, the UI reflects the change by **re-browsing
authoritative state**, never by faking a live update. The contract is:

1. **On the next real History Commit.** Any later capture/pin/remove/revise/
   retention commit advances `ChangePosition` and wakes a live `observe(.search)`
   naturally; the observer's fresh `SearchCorpusSnapshot` includes any enrichment
   text persisted since (`V2-01` §4.1) and reflects any toggle. The UI does
   nothing extra; v1's observer delivers the page.
2. **On a fresh `browse(.search)` / `browse(.recent)` / `details(for:)` /
   `enrichmentStatus(for:)` / etc.** A one-shot read **always** reflects current
   state (`04` §3 read-after-commit; `V2-01` §8 `enrichmentStatus` reads scalar
   columns). The UI issues a fresh browse on:
   - an **explicit user action** that implies the user wants current state: opening
     the search field, opening a row's detail, toggling a setting, pulling up the
     audit log, re-opening the window;
   - a **completion the UI can observe without a History Commit** — currently only
     the P2 predicate-change self-heal (§4.3). There is **no** enrichment-OCR
     completion stream in V2-01's public surface (OPEN-1); the UI does not poll.
3. **Never claim live freshness it cannot deliver.** A status indicator sourced
   from `enrichmentStatus(for:)` is labeled with the value at fetch time and is
   **not** advertised as real-time. A row's enrichment badge may read `.pending`
   after OCR has in fact completed, until the next re-browse; the UI states this
   honestly (the badge means "pending at last refresh," not "pending now"). This
   mirrors v1's own honesty: a one-shot `browse` may return a valid historical
   snapshot (`04` §2).

```swift
@MainActor
@Observable
final class HistoryListViewModel {
    private let history: any ClipboardHistory
    private let enrichment: (any EnrichmentHistory)?     // nil if V2-01 not admitted
    private var pageTask: Task<Void, Never>?
    private(set) var recentPage: HistoryPage?            // the last browsed page (re-browse target)

    func refresh() {                                       // explicit re-browse (contract §4.2.2)
        pageTask?.cancel()
        pageTask = Task { [weak self] in
            guard let self else { return }
            // A one-shot browse ALWAYS reflects current state (04 §3).
            let page = try? await self.history.browse(.init(kind: .recent, limit: 200))
            self.recentPage = page
        }
    }

    func toggleEnrichment(_ enabled: Bool) async {         // not-live-observed write
        try? await enrichment?.setEnrichmentEnabled(enabled)
        // setEnrichmentEnabled advanced no ChangePosition; a live observe(.search)
        // is NOT woken. Refresh explicitly so the next render reflects the toggle.
        refresh()
    }
}
```

### 4.3 The P2 predicate-change self-heal (the one live-refresh exception)

`V2-06` P2 is the **single exception** to "not live-observed." A locale/enable
change alters the *predicate* an `observe(.search)` evaluates, not the corpus.
Leaving an active `observe(.search)` silently stale under a new predicate would be
a coherence deviation, so P2's config writes additionally yield an internal
**predicate-change signal** (a `HistoryInvalidation`-peer wake-up internal to
`HistoryStorage`, `04` §4) carrying the **current** `ChangePosition` (not advancing
it). The `observe(.search)` consumer honors this signal as a distinct wake
condition and re-queries under the new predicate/locale **at the current position**
(`V2-06` §4.5 C-M5).

Consequence for UX: an active search stream **self-heals** on P2 toggle/locale
change — the UI need not imperatively re-browse (though a one-shot
`browse(.search)` always reflects the current predicate on its next call). This is
the **only** V2 config write that live-refreshes an active observer; enrichment,
cache, gateway, and journal config writes do not (they have no predicate-change
signal). V2-07 states this asymmetry explicitly so a future contributor does not
assume the self-heal generalizes.

### 4.4 The contract, summarized

> **UI freshness rule.** An active `observe(.recent)`/`observe(.search)` reflects
> (a) every History Commit (v1 + V2-02 retention + V2-05 external writes that route
> through the Authority) via standard snapshot replacement, and (b) for an active
> `observe(.search)` only, a P2 predicate/locale change via the predicate-change
> self-heal (`observe(.recent)` is predicate-independent and ignores the
> predicate-change signal, `V2-06` §4.5). It does **not**
> reflect enrichment persistence, enrichment/cache/gateway/journal config writes,
> or OCR completion until the next History Commit or a fresh one-shot read. The UI
> never fabricates a live update for the latter; it re-browses on explicit user
> action and states pending-state honesty.

## 5. Per-capability UX surfaces

Each subsection consolidates the `§12`/`§13` UX hooks the part doc deferred to
V2-07, states the source DTO, the live/not-live classification, the settings
exposure, and the data-practice disclosure. **All rendering is on the main actor
from `HistoryCore` DTOs only** (`V2-00` §6.6).

### 5.1 V2-01 Enrichment (E1)

- **Enrichment status indicator.** A `HistoryRow`-adjacent badge
  (pending/ready/failed/not-applicable) sourced from
  `enrichmentStatus(for:)` (`V2-01` §8). Rendered only on image/PDF-bearing rows
  where the status is not `.notApplicable` (the `HistoryRow.typeIdentifiers`
  pre-filter bounds the badge to that subset). **Per-page fan-out (OPEN-6):** the
  badge is a per-row `enrichmentStatus(for:)` read — an N-way fan-out over the
  image/PDF-bearing rows on a page, since V2-01's current public surface exposes
  **no batch status read** (`V2-01` §8). The fan-out is bounded by `UX-PERF-1`
  (§12) or collapses to one read if V2-01 ships `enrichmentStatuses(for:)`
  (OPEN-6); the badge is **not live-observed**
  (§4.1): `persistEnrichment` and `setEnrichmentEnabled` advance no
  `ChangePosition`. The UI re-browses on the next History Commit and on explicit
  user action (§4.2). **Pending-state honesty (OPEN-1, closure in §14):** because
  V2-01 exposes no OCR-completion stream, a badge may read `.pending` after OCR
  completed, until the next re-browse; the accessibility label states "pending at
  last refresh," not "pending now."
- **Search match transparency.** When enrichment is on, an OCR-text match shows as
  a `SearchPresentation` snippet (UTF-16 ranges into the enrichment excerpt), using
  the **existing v1 public type unchanged** (`03b` §8; `V2-01` §12 "no new public
  DTO"). No new DTO is required for the match itself.
- **Enrichment-enabled setting (write-only until OPEN-3).** A toggle bound to
  `setEnrichmentEnabled(_:)` (`V2-01` §8); toggling off stops new derivation but
  **does not delete** existing rows. **The toggle is write-only against V2-01's
  current public surface:** `EnrichmentHistory` exposes no panel-level
  `enrichmentEnabled()` read (`V2-01` §8), so on panel-open the toggle cannot
  faithfully reflect the current capability state until V2-01 adds the read
  (OPEN-3); until then the toggle ships as set-only with that cost disclosed.
  OCR recognition language and accurate/fast level are **fixture-locked, not
  user-configurable** in V2-01 (`V2-01` §12); they are not surfaced as settings.
- **Data-practice disclosure.** V2 durably persists and full-text-indexes the
  textual content of copied images/PDFs — a content-sensitivity amplification
  (`V2-01` §9 Record 6). The enablement UI states this practice (OCR text of copied
  images is stored and searchable; it is processed on-device; removed-item OCR text
  lingers until the lazy sweep, with non-wall-clock-bounded latency for inactive
  users). This disclosure is the UX half of V2-01's Record 6.

### 5.2 V2-02 Retention (R1/R2/R3)

- **Retention settings.** Three controls bound to the `HistoryAction`
  `.setRetentionPolicies(HistoryRetentionPolicies)` case (`V2-02` §8.1): an age
  field (R1 `AgeRetention.maxAge`), a storage-byte budget field (R2
  `StorageRetention.maxTotalBytes`), and per-item revision count/byte fields (R3
  `RevisionRetention`). Disabling a dimension sends `nil` for that dimension's
  `Optional` (age/storage/revisions); for revisions specifically, a
  `RevisionRetention` with both sub-thresholds `nil` is normalized to
  `revisions == nil` per `V2-02` §3.1 (the both-nil rule is revisions-only, not
  all three dimensions). The **count** control stays bound to the **v1**
  `.setRetentionPolicy(maximumUnpinnedItems:)` (separate action; `V2-02` §8.1).
  Byte/age thresholds use locale-appropriate number formatting (§10).
- **Receipt feedback.** A `.retentionPoliciesSet(retiredItems:prunedRevisions:)`
  receipt surfaces "N items retired, M older revisions pruned" (transparent
  data-minimization feedback, `V2-02` §12). A `.capacityExceeded(.storageBytes)`
  failure surfaces "storage budget too low for pinned items" guidance (recovery:
  unpin items or raise the budget, `V2-02` §8.3). Capture (R1/R2) and revise
  (R2/R3) fold their retirements/prunes into the primary receipt
  (`.inserted`/`.coalesced`/`.revised`), which carries **no** retired/pruned count
  — consistent with v1; those side-effects are observable only via the
  `.recent`/`.search` snapshot and `details(for:)`.
- **Observation.** V2-02 retirements/prunes **are** History Commits; an active
  `observe(.recent)`/`observe(.search)` reflects them via standard snapshot
  replacement (§4.1, contrast table). R3 pruning changes `HistoryDetails.revisions`
  on the next `details(for:)`. (Honest cost: a `.setRetentionPolicies` that prunes
  across many items advances `ChangePosition` once and spuriously wakes every
  `.recent`/`.search` subscriber even though inactive-revision pruning does not
  change the recent/search snapshot — a visible list re-render with no content
  change for the user — accepted, `V2-02` §12.)
- **Live storage indicator.** **Not available** from V2-02's public surface
  (OPEN-2): V2-02 exposes the budget and the receipt, not a current-retained-bytes
  read. The settings panel shows the configured budget; a live usage readout
  requires a V2-02 protocol extension and is not introduced by V2-07.

### 5.3 V2-03 Change Journal & Reconnect (J1) — if product-approved

- **Reconnect status / "recently removed" surface (only if V2-03 trigger (b)
  fires).** A main-actor view consuming `ReconnectHistory.changes(since:)`
  (`V2-03` §6.3). Observation is snapshot-replacement (§4): `ReconnectHistory` is
  **pull-only** (`changes(since:)`/`currentReconnectAnchor()`; it exposes **no**
  push notification — `V2-03` §6.3), so the surface refreshes only on an explicit
  user pull/re-open; a stale "recently removed" list is expected until the user
  refreshes (mirrors §4.2.3 pending-state honesty). It does **not** subscribe to a
  delta stream — the v1 live observer is untouched (D28, `V2-03` §13). **OPEN-8
  (closed; parallel to OPEN-1, closure narrative in §14):** `V2-03` §13 (amended)
  matches this pull-only contract; the stale "reconnect notification" wording
  OPEN-8 escalated has been amended, closing the escalation on the same terms as
  OPEN-1 (§14).
  **Best-effort fidelity caveat (`V2-03` §13 C2-m9):** a kind-based "recently
  removed" filter sees
  `.remove`/`.retire`/`.clearAll`/`.clearUnpinned` rows directly, but a
  **capture + retention-retire** commit records `.insert` as the primary with the
  retired items folded into `affectedItemIDs` (`V2-03` §4.3 primary-kind-only
  contract) — so a pure kind filter **misses** those retirees. The surface is
  scoped to the primary-kind rows it can soundly report and avoids claiming
  completeness over folded retirees (the `§4.3` consumer obligation to
  cross-reference a mirror is not imposed on the UI).
- **Advanced settings (gated on OPEN-5).** A journal-retention window control
  (age/count), a collection-cache enable/disable toggle, and a "flush change
  journal now" control. **These controls are ABSENT from V2-07 until V2-03 ships a
  public `JournalAdminHistory: Sendable` protocol** (OPEN-5): today
  `setJournalConfig(...)`/`compactJournal()` live on an `internal extension
  HistoryAuthority` and `JournalConfigRow` is an `internal @Model` (`V2-03`
  §10.3/§4.6), so the UI — which imports only `HistoryCore` (`01` §8) — cannot
  reach them. `JournalAdminHistory` (mirroring `GatewayAdminHistory`/
  `ThumbnailCacheHistory`) would expose `setJournalConfig(...)` (clamped to
  `JournalLimits`, `V2-03` §4.5), `compactJournal()` (compacts to the current
  floor, expiring live cursors), and a `journalConfigStatus()` read; until it
  ships, §8.2's `journalAdmin` cast is `nil` and this section renders nothing
  (§8.2 admission rule). All not-live-observed (§4.1) once shipped.
- **Resync notice.** A journal rebase bumps `generation` (`V2-03` §9.2); surfaced
  as a one-time "history resynced" notice (consumers holding old cursors get
  `.generationMismatch` and resync).
- **Not shipped unless exposed.** If J1 is admitted on the G2 performance trigger
  alone (no reconnect product requirement), only the advanced settings (cache/
  journal hygiene, not reconnect) are exposed — and only once OPEN-5 ships; the
  reconnect surface is absent.

### 5.4 V2-04 Materialization caches (C1/C2/C3 + S1 thumbnail)

- **Transparent availability.** Thumbnail availability is **unchanged** from v1
  (`V2-04` §12): a caller observes the same availability and the same
  `.staleContent`/`nil` semantics. No "served from cache" indicator is exposed (it
  is an internal latency detail).
- **Disk-cache settings (if C2 admitted).** A toggle bound to
  `setDiskThumbnailCacheEnabled(_:)` (default off, `V2-04` §6.4) and a size-cap
  control bound to `setMaxDiskThumbnailCacheBytes(_:)`, both rendered from
  `ThumbnailCacheStatus` (`V2-04` §10). A best-effort "disk bytes used" readout
  sourced from `thumbnailCacheStatus()` — **approximate** (`diskBytesUsed` is an
  ephemeral in-memory counter, rebuilt by the background sweep; reports 0 until the
  first post-restart sweep completes, `V2-04` §10). **Freshness honesty (§4.2 #3,
  applied symmetrically with the enrichment `.pending` badge, §9.2):** the
  readout's visible label and accessibilityValue state "approximate, pending
  refresh" whenever `diskBytesUsed` is in its pre-sweep (0) state (or the readout
  is qualified as "approximate" at all times) — a user never reads a bare "0 bytes"
  as "cache empty." A "clear disk cache now" button bound to
  `clearDiskThumbnailCache()` is the immediate-reclaim control.
- **Observation.** Cache config changes advance no `ChangePosition` and are
  **not live-observed** (`V2-04` §12); the UI re-browses on toggle (§4.2).
- **Data-practice disclosure.** Enabling the disk cache stores thumbnail previews
  of copied images on disk (in the Caches directory) for the eviction window — a
  new durable derived-preview exposure (`V2-04` §11 Record 6). The enablement UI
  states this practice (previews are downsampled to ≤ 2,048 px/axis, `06` §2; the
  Caches directory is excluded from iCloud backup by default (`V2-04` §11 Record 6;
  the explicit-flag defense-in-depth decision is tracked as C2-SECURITY-2 in
  `V2-04` §13); the exposure window is the eviction cap). **Removal-latency disclosure (`V2-04` Record 6):** removing
  an item does **not** immediately delete its on-disk thumbnail preview — the disk
  file lingers until the background sweep reclaims it (`V2-04` §6.5); the "clear
  disk cache now" control is the immediate-reclaim remedy. This is surfaced
  symmetrically with V2-01's OCR-text removal-latency disclosure (§5.1).

### 5.5 V2-05 External Gateway & Audit (X1/X2)

- **Connection management.** Enroll (the App Intents connection is pre-bootstrapped
  at `open`; the UX offers "Enable Siri/Shortcuts access"), revoke, and view active
  connections — built from `ConnectionDTO` (`V2-05` §7.2) via `GatewayAdminHistory`
  (in-app, main-actor only; **not** registered in `AppDependencyManager`, `V2-05`
  §7.2).
- **Capability grants.** Toggle `browse`/`readContent`/`manage` per connection
  (`V2-05` §3.2). Deny-by-default is surfaced explicitly. The
  `browse`/`readContent` **split** is the content-exfiltration control and is
  surfaced as **two distinct data practices** (`V2-05` §3.2): "search your history"
  (metadata: titles + ≤322-Character snippet) vs "read full content" (passwords,
  tokens, secrets). `.manage` implies `.browse` but **not** `.readContent`
  (`V2-05` §3.2) — the implication is shown in the grant UI.
- **Audit log viewer.** A paginated `OperationRecordDTO` list (capability, kind,
  outcome, `failureKind`/`denialReason`, timestamp, `affectedItemIDs` count) via
  `auditLog(since:)`. **Privacy-preserving:** no query text, no returned content
  (`V2-05` §7.2 `OperationRecordDTO`). A "compacted-before" indicator when the read
  floor is hit (`.auditCompactedBefore`); a rebase banner when a discarded
  `[oldFloor, newFloor)` range is present (`V2-05` §5.6, CRIT-M2). **Verifiability-
  loss disclosure (D36):** because the audit chain is honestly bounded (tamper-
  evident, not tamper-proof), both the compacted-before indicator and the rebase
  banner disclose that audit records below the read floor / in the discarded
  `[oldFloor, newFloor)` range are **no longer verifiable** — the user-relevant
  consequence a privacy-conscious user seeing the banner needs.
- **Privacy/transparency indicators.** "Siri searched your history N times since
  …"; rate-limit transparency via `denialReason == .rateLimited` (`V2-05` §7.3);
  data-practice disclosure for `browse`/`readContent`/`manage` exposure and the
  audit log's tamper-**evident** (not tamper-**proof**) bound (`V2-05` D36).
- **Revocation immediacy.** Revocation is immediate-from-UX in the sense that the
  UX action calls `revokeConnection`/`revokeCapability` through the Authority; the
  **authoritative** gate is the in-closure recheck at the save boundary (`V2-05`
  §5.1/§5.2, D33), so a revoked connection's in-flight request is rejected there.
  The UI does not claim "instant" — it claims "revoked; the next request is
  rejected."
- **Audit-persists-after-revoke disclosure (`V2-05` Record 6).** Revocation stops
  new requests but does **not** delete the historical `OperationRecord`s of past
  accesses (append-only audit; cleared only via compaction `V2-05` §4.5 or rebase
  §5.6, both admin operations). The revocation UI states this — the audit trail of
  past reads persists until an admin compaction/rebase. This is surfaced
  symmetrically with V2-01's and V2-04's removal-latency disclosures (§5.1/§5.4).
- **Observation.** All `GatewayAdminHistory` operations advance no
  `ChangePosition` and yield no `HistoryInvalidation` (`V2-05` §13); the audit
  viewer and grant list **re-read on demand** (open the panel, pull-to-refresh),
  like V2-01 enrichment status. No live audit feed.

### 5.6 V2-06 Platform grafts (P1/P2/P3)

- **P2 (localized search).** A supported-locales setting + enable toggle, built
  from `LocalizedSearchStatus` (`V2-06` §4.5) via `LocalizedSearchHistory`. The
  supported-locale list is fixture-locked (`LocalizedSearchLimits`,
  `V2-06` §4.5); selecting an unsupported identifier is rejected

## 6. Settings consolidation

### 6.1 Where V2 settings live

V2 settings live in a **V2 settings panel in `PresentationUI`** (composed by
`ClipyApp`), bound to the V2 distinct-concern protocols and the V2-02
`HistoryAction`. (No v1 settings panel exists - v1 `.setRetentionPolicy` has no
documented UI surface (`01` §6 lists views/observable state/selection/window
behavior only) - so this consolidated panel is new `PresentationUI` surface V2-07
itself introduces, not a v1-inherited location; it is part of V2-07's new-surface
inventory, §1.1.) There is **no settings store on the History schema** (Record 5,
§11): every V2 setting is either (a) a `HistoryAction` payload (V2-02
`.setRetentionPolicies`, persisted by `V2-02` §5.6
`HistoryMutation.setRetentionPolicies` to `RetentionExpansionConfigRow`) or (b) a
distinct-concern protocol method that writes a sibling-doc config singleton
(`EnrichmentConfigRow`, `ThumbnailCacheConfigRow`, `LocalizedSearchConfigRow`, the
V2-05 Connections/Grants rows). **Exception — journal config (OPEN-5):** V2-03's
`JournalConfigRow` has **no public writer protocol** today (`setJournalConfig`/
`compactJournal` are on an `internal extension HistoryAuthority`, `V2-03` §10.3),
so the journal advanced-settings controls have no protocol method to bind until
V2-03 ships a public `JournalAdminHistory` (OPEN-5); they are absent until then
(§5.3/§8.2). The UI holds `Sendable` protocol references and `await`s the write;
it stores **no** setting itself.

A V2 user-preference that is **not** a History concern (none identified in V2's
admitted set — the locale identifier is a History concern on
`LocalizedSearchConfigRow`) would live in a standard `UserDefaults`/settings-store
outside the History schema, **not** in `HistorySchemaV2`. V2-07 introduces no such
preference.

### 6.2 Classification: `HistoryAction` vs distinct-concern protocol

This classification governs whether a setting write is live-observed (§4).

| Setting | Surface | Kind | Advances `ChangePosition`? | Live-observed? |
|---|---|---|---|---|
| Maximum unpinned count (v1) | `.setRetentionPolicy` | `HistoryAction` (v1) | yes (when value/victims change) | yes |
| Age / storage-byte / revision retention (V2-02) | `.setRetentionPolicies` | `HistoryAction` (V2-02) | yes (D6, `V2-02` §4.5) | yes |
| Enrichment enable (V2-01) | `EnrichmentHistory.setEnrichmentEnabled` | distinct-concern protocol | no | no |
| Disk-cache enable / size / clear (V2-04) | `ThumbnailCacheHistory.*` | distinct-concern protocol | no | no |
| External connection/grant admin (V2-05) | `GatewayAdminHistory.*` | distinct-concern protocol | no | no |
| Journal retention / cache toggle / compact (V2-03) | pending `JournalAdminHistory.*` (OPEN-5; today internal `V2-03` §10.3) | distinct-concern | no | no |
| Locale enable / locale select (V2-06 P2) | `LocalizedSearchHistory.*` | distinct-concern protocol | no | **yes (predicate-change self-heal, §4.3)** |

The rule mirrors the sibling-docs' own classification: a setting that mutates
history **content** (retirement/prune) is a `HistoryAction`; a setting that
configures a **derivation/cache/gateway/projection** is a distinct-concern protocol
(`V2-00` §6.5; `V2-01` §8; `V2-05` §7.2 "why admin operations are NOT
`HistoryAction` cases").

### 6.3 Settings-panel shape

The panel is organized by capability, not by v1/V2 boundary. (The count-vs-
age/storage/revision action split (§5.2) is a deliberate fragmentation point: the
panel renders the count control and the V2-02 age/storage/revision controls as one
unified "Retention" group with consistent receipt feedback, rather than splitting
them across capability sections.) Each section renders
from the capability's status DTO on panel-open (a one-shot read, §4.2.2) and writes
through the corresponding protocol/action. The panel itself is a UI-internal
`@Observable` view model (§8.3); it owns no durable state.

### 8.1 Module and target placement

- **No new target.** V2-07 adds SwiftUI views and `@Observable` view models to

  V2-07 (a sibling doc that needs a new public DTO or protocol owns that change).
- **Imports.** `PresentationUI` imports only `HistoryCore` (+ SwiftUI), exactly as
  v1 (`01` §8 forbids PresentationUI from importing `HistoryDomain`/`HistoryStorage`;
  the target graph in `01` §1 admits only `HistoryCore` + SwiftUI). The V2 distinct-concern
  protocols V2-07 consumes (`EnrichmentHistory`, `ThumbnailCacheHistory`,
  `GatewayAdminHistory`, `LocalizedSearchHistory`, `ReconnectHistory`, and — once
  V2-03 ships it (OPEN-5) — `JournalAdminHistory`) are public protocols **in
  `HistoryCore`** (each declared in its owning doc); the UI sees them through the
  same `HistoryCore` import. `BlobStreamingHistory` (`V2-06` §5.4) is public in

  `SwiftData`/`HistoryStorage`/`HistoryDomain`/AppKit/Vision/PDFKit import is added

- **No new actor, no new framework import in the UI.** All V2 derivation/cache/
  gateway/audit work runs on sibling-doc actors inside `HistoryStorage`
  (`V2-01` §6.2, `V2-04`, `V2-05`); the UI only `await`s `Sendable` DTO returns on
  the main actor.

### 8.2 The protocol cast pattern in `ClipyApp`

`ClipyApp` constructs `SwiftDataHistory` (the v1 composition root, `01` §2) and
casts it to each V2 distinct-concern protocol only when that capability is
admitted. A v1 `ClipyApp` that ignores V2 behaves exactly as on v1; V2 surface is
opt-in per protocol.

```swift
@main
struct ClipyApp: App {
    @MainActor
    init() {
        // v1 composition root (01 §2). history is `any ClipboardHistory`.
        let history = SwiftDataHistory.open(...) as any ClipboardHistory

        // V2 distinct-concern casts — each is nil-conditional on admission.
        // SwiftDataHistory conforms to every admitted protocol additively
        // (V2-01 §8.1, V2-04 §10.1, V2-05 §7.4, V2-06 §4.5).
        let enrichment       = history as? any EnrichmentHistory
        let thumbnailCache   = history as? any ThumbnailCacheHistory
        let gatewayAdmin     = history as? any GatewayAdminHistory
        let localizedSearch  = history as? any LocalizedSearchHistory
        let reconnect        = history as? any ReconnectHistory
        // Absent until V2-03 ships a public JournalAdminHistory (OPEN-5): today
        // setJournalConfig/compactJournal are internal (V2-03 §10.3), so this cast
        // is nil and the journal advanced-settings section renders nothing.
        let journalAdmin     = history as? any JournalAdminHistory

        _viewModel = .init(
            history: history,
            enrichment: enrichment,
            thumbnailCache: thumbnailCache,
            gatewayAdmin: gatewayAdmin,
            localizedSearch: localizedSearch,
            reconnect: reconnect,
            journalAdmin: journalAdmin)
    }
}
```

The cast (`as? any P`) is the V2 admission check at the composition root: a
protocol whose sibling doc has not shipped the conformance yields `nil`, and the
corresponding UI section is absent. No runtime feature flag is introduced; the
cast is the flag.

### 8.3 Main-actor `@Observable` presentation state

Presentation state is `@MainActor @Observable` view models holding only DTOs and
`Sendable` protocol references — the Swift 6 evolution of v1's "observable
presentation state" (`01` §6). `@Observable` is the Observation framework macro
(`Observation/observable()`, **macOS 14.0+**, cycle-1 MCP-verified; present on
macOS 26). The view models never store `@Model`/`ModelContext`/`PersistentIdentifier`
or Domain state; they store DTO snapshots and re-fetch on the contract of §4.

```swift
@MainActor
@Observable
final class EnrichmentSettingsViewModel {
    private let enrichment: any EnrichmentHistory
    // OPEN-3: EnrichmentHistory exposes no panel-level `enabled` read (V2-01 §8);
    // until V2-01 adds one (e.g., `enrichmentEnabled()`), the toggle is WRITE-ONLY
    // — `enabled` below reflects only the last user-set value, not authoritative
    // capability state. The panel discloses this (§5.1).
    private(set) var enabled: Bool = false          // last user-set value (OPEN-3)

    func load() async {                              // one-shot read (§4.2.2) — NO-OP until OPEN-3
        // V2-07 adds no config-read DTO; load() is a no-op until V2-01 ships
        // `enrichmentEnabled()` (OPEN-3).
    }
    func setEnabled(_ value: Bool) async {           // not-live-observed write
        try? await enrichment.setEnrichmentEnabled(value)
        enabled = value                              // reflect the user-set value (write-only)
        // No authoritative re-read is possible until OPEN-3.
    }
}
```

Where work must cross an isolation boundary (e.g., a detached `Task` deriving a
preview), only `Sendable` DTO values cross — the `@MainActor`-isolated
`@Observable` view model itself never crosses (a `@MainActor`-isolated reference
type is not `Sendable` in the cross-task sense; `@Observable` classes are not
`Sendable` by default), mirroring v1's boundary rule (`01` §6). No `@unchecked
Sendable` or `nonisolated(unsafe)` is introduced (proof gate `UX-COMPILE-2`).

### 8.4 No leakage

The UI boundary rule is v1's unchanged (`01` §6, §8): only immutable `Sendable`
DTO values cross to the main actor. No `@Model`, `ModelContext`, lazy relationship,
`PersistentIdentifier`, AppKit object, `NSImage`, `CGImage`, `VNRecognizedTextRequest`,
`PDFDocument`, `NSFileCoordinator`, audit hash chain, or `HistoryStorage`/`HistoryDomain`
internal crosses. The V2 DTOs the UI consumes are all `Sendable` value types
declared `public` in `HistoryCore` (Foundation-only). `UX-COMPILE-1` is the
compile/import-gate proof; the v1 source gate (`01` §9) is **unchanged** for
`PresentationUI` (no new framework import).

### 8.5 SwiftUI Preview adapter

SwiftUI previews use the v1-sanctioned scripted `ClipboardHistory` adapter (`01` §4
"Preview/scripted History"), extended to conform to the V2 distinct-concern
protocols the preview exercises — returning fixture DTOs (`EnrichmentStatus.ready`,
a fixed `OperationRecordDTO` list, etc.). This adapter is **not** a substitute for
`SwiftDataHistory` semantic tests (`01` §4); it only constructs UI preview state.

## 9. Accessibility

(State-3 acceptance, `06` §1 point 3.)

1. **Every new status/indicator/control is accessibility-labeled.** The enrichment
   badge, the retention receipt feedback, the disk-cache "bytes used" readout, the
   connection/grant toggles, the audit-log rows, the locale picker, and the
   journal-advanced-settings controls each carry an `accessibilityLabel`
   (SwiftUI View modifier; availability gated `UX-PLATFORM-2`) and, where the state
   is not obvious from the label, an `accessibilityValue`/`accessibilityHint`.
   Search-match transparency (a `SearchPresentation` enrichment snippet) is
   announced as part of the row's accessibility content.
2. **Pending-state honesty (§4.2).** A not-live-observed indicator's accessibility
   value states the fetch-time value ("pending at last refresh"), never a claim of
   real-time freshness it cannot deliver. This applies symmetrically to the disk-
   cache "bytes used" readout (§5.4): its visible label and accessibilityValue
   state "approximate, pending refresh" while `diskBytesUsed` is in its pre-sweep
   (0) state (`V2-04` §10), mirroring the enrichment `.pending` badge — a user
   never reads a bare "0 bytes" as "cache empty."
3. **Dynamic Type / contrast.** V2 surface honors the system text-size and
   contrast settings; no V2 indicator relies on color alone (the enrichment badge
   pairs an icon + label, not color only). This is v1's state-3 acceptance applied
   to V2 surface.
4. **Audit-log readability.** The audit viewer's `OperationRecordDTO` fields are
   rendered as localized phrases ("Siri read full content of 1 item, succeeded"),
   not raw enum raw-values, so VoiceOver reads a sentence, not `capability=2`.

## 10. Localization

(State-3 acceptance, `06` §1 point 3.)

1. **All V2 strings are `LocalizedStringResource`.** Every user-facing label,
   hint, disclosure, receipt feedback string, and accessibility label is a
   `LocalizedStringResource` (Foundation; **macOS 13.0+**, cycle-1 MCP-verified;
   present on macOS 26) backed by a Localizable strings catalog. No V2 string is a
   raw `String` literal in the user path.
2. **P2 locale-aware search is a separate concern from UI localization.** The
   search-projection locale (P2, `V2-06`) governs how `browse(.search)` matches
   text (case/diacritic/width folding under the selected locale). UI localization
   governs the language of labels and disclosures. The two are independent: a user
   may run the UI in French while searching under an English locale, or vice versa.
   The settings panel makes this explicit (the locale picker is under "Search," not
   under "Language").
3. **Locale-appropriate number formatting.** Byte thresholds (R2
   `maxTotalBytes`, V2-04 `maxDiskBytes`) and age thresholds (R1 `maxAge`) use
   locale-appropriate `Formatter`s (`ByteCountFormatter`/`DateComponentsFormatter`
   or their SwiftUI equivalents); a 5,000-item count is formatted with the locale's
   grouping separator. P2 (locale-sensitive formatting) applies.
4. **Plurals.** Receipt feedback (".retentionPoliciesSet(retiredItems:
   prunedRevisions:)") and audit counts use plural-aware localized strings
   (stringsdict / String Catalog plurals) so "1 item retired" vs "5 items retired"
   localize correctly per language.
5. **Required disclosure strings (the UX half of sibling-doc Record 6s).** The
   following are each required user-facing `LocalizedStringResource` entries,
   surfaced symmetrically so no sibling doc's content-sensitivity latency is hidden
   while another's is shown: V2-01 OCR-text removal-latency (§5.1), V2-04 disk-
   thumbnail-lingers-after-remove + the "clear disk cache now" immediate-reclaim
   remedy (§5.4), V2-05 audit-persists-after-revoke (§5.5), and the audit
   verifiability-loss string shown with the rebase banner / compacted-before
   indicator (§5.5, "audit records before this point are no longer verifiable").
   Absolute timestamps in audit/privacy indicators (the "since [date]" anchor,
   `OperationRecordDTO.requestedAt`/`committedAt` renderings) use a locale-
   appropriate absolute `DateFormatter` (or SwiftUI's equivalent), alongside the
   duration/byte formatters of (3).
