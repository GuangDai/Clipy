## 1. Executive summary

HistoryCore is **sound**. It is a thin, spec-pinned Foundation-only value/protocol layer — IDs, coherence tokens, the `ClipboardHistory` protocol, action/receipt/DTO enums-and-structs, and the `HistoryLimits` admission-value — with **zero correctness defects and zero structural failures** confirmed in this cycle. There are **no Critical or Major findings**; all 20 confirmed findings are Minor (9) or Nit (11), concentrated in surface hygiene (an over-wide `public init?`, latent `Hashable` on byte-payload DTOs) and a **systematic happy-path-only test bias** that never exercises the rejection branches which are the module's primary safety claim. The single most important framing for any reader: the module under review is healthy, and the genuine read-path memory risk (the G8-deferred inline-value DTO tax, transient ~384 MiB `details()` hydrate peak) lives **across the boundary in HistoryStorage** — HistoryCore can only describe it from the DTO seam outward. The highest-leverage fix is a one-sentence spec edit (give the read-path memory tax a G8 owner), and the highest-leverage code change is tightening `HistoryLimits.init?` from `public` to `package` before the symbol-surface snapshot cements the wider surface as load-bearing.

## 4. Complexity analysis

**`HistoryAuthority.details()` (cross-boundary; described from the DTO seam).** Current: **time O(revision text)** per revision to project, **space O(total revision bytes)** transient — the full `revisionStateBlob` (up to 256 MiB per `06 §2`) is decoded into a live `HistoryItemState` and held throughout `details()` while summaries are projected. Reduction target: **space O(max single revision bytes)** via an incremental summary-only hydrate that decodes one revision, projects its `RevisionSummary`, and releases that revision's bytes before decoding the next. Spec-neutral (`§9 RevisionSummary` carries no bytes); peak drops toward ~192 MiB with NO DTO/schema change.

**`ContentProjector.project()` per-revision (cross-boundary).** Current: **O(revision text)** — builds the full `searchBody` (join + truncate to 256 KiB) and `effectiveTypeIdentifiers` even when only `.title` is read. Reduction target: **O(title text)** via a `projectTitleOnly(content:limits:)` that stops after the first textual representation's first line. Up to 100 revisions × ~256 KiB of discarded string work removed.

**`HistoryItemID.<` / `RevisionID.<` (`Identity.swift:23-29`, `41-47`).** Current: **O(16) byte scan** + two `withUnsafeBytes` buffer setups + a closure hop per comparison. Reduction target: **O(1)** — reinterpret the 16-byte `uuid_t` as two big-endian `UInt64` words and compare (identical byte-lexicographic semantics). Constant-factor only; the comparator sits behind `lastCopiedAt` equality on rare ties, so the win is unmeasurable today but the simpler form is strictly better.

**Compiler-synthesized `Hashable` on byte-payload DTOs.** Current: **O(total bytes)** hashing if ever triggered (`HistoryRepresentation`/`HistoryDetails`/`PastePayload`/`ThumbnailPayload`, up to ~128–192 MiB per value). Reduction target: **O(1)** by dropping `Hashable` to `Equatable` (zero `Set`/`Dict` key uses today) — removes the latent O(bytes) footgun entirely.

## 5. Efficiency notes

- **`details()` wasted projection.** Stop calling `ContentProjector.project()` per revision just to read `.title` — `project()` also builds + truncates the `searchBody` (256 KiB) and `effectiveTypeIdentifiers` per revision, all discarded. A `projectTitleOnly` variant removes up to ~25 MiB of discarded string work per `details()` on a maxed item.
- **`details()` transient peak.** Replace hydrate-all-then-project (full `canonicalBlob` AND `revisionStateBlob` decoded into a live `HistoryItemState` held throughout `details()`) with an incremental summary-only decode that releases each revision's bytes before decoding the next — removes the ~384 MiB transient peak.
- **`HistoryItemID`/`RevisionID.<`.** Replace the 16-byte `withUnsafeBytes` + `lexicographicallyPrecedes` (closure hop + buffer setup per call) with a two-`UInt64` word compare — eliminates per-comparison scan overhead on the corpus pre-order path.
- **`Hashable` on byte-payload DTOs.** Drop it (keep `Equatable`) — removes the synthesized O(total bytes) hash that would feed ~128–192 MiB into a `Hasher` if any DTO ever lands in a `Set`. Zero current trigger; pure latent-footgun removal.
- **`HistoryLimits.init?` access.** Tighten `public`→`package` — removes an entire category of wasted reasoning about external-bound forgery and lets the symbol-snapshot gate start protecting the standard-only contract instead of cementing the over-wide surface.

## 6. Security & edge-case notes

HistoryCore holds no secrets and does no I/O; "security" here reduces to **admission-value validation completeness** and **identity determinism**.

- **`HistoryLimits.init?` is the module's primary safety claim.** At baseline it
  accepted preconstructed ranges, so invalid ordering trapped before failable
  validation; the audit's claim that `uncheckedBounds` avoided that trap was
  later disproved by run 31449140919. It also lacked the representation ≤
  proposed-revision relation, and no rejection branch had direct tests. The
  endpoint-based package initializer and parameterized suite now own all three
  gaps; supported rerun proof remains.
- **`ContentVersion.init(rawValue:)` accepts 0** (which `06 §7.4` treats as corrupt decode) — but the only minting path (`decodeContentVersion`) guards `rawValue>=1` first, so the claimed exploit path does not exist. Defense-in-depth nit only.
- **Identity determinism** rests on `HistoryItemID.<`/`RevisionID.<` byte ordering, never directly asserted by tests; `<` is the final tie-break behind `lastCopiedAt` equality (rare), and the cited regression vector (uuidString vs raw byte) is a no-op for UUIDs, so real but small.

## 7. Concurrency / isolation notes

- **`ClipboardHistory: Sendable`** and every HistoryCore value is `Sendable`/`Hashable` — the layer is correctly actor-isolation-neutral by design.
- **`observe(_:)` returns `AsyncThrowingStream<HistoryPage, Error>`** (`ClipboardHistory.swift:60-62`) — the only protocol method that cannot deliver a typed `HistoryFailure`. This is a **deliberate spec choice** (`03a §3` pins `Error`), NOT a Swift limitation: `AsyncThrowingStream` is generic over `Failure`, so `AsyncThrowingStream<HistoryPage, HistoryFailure>` is legal. Documentation nit only.
- **`RevisionPreparationActor`** (`ActorStubs.swift:122`) holds only the immutable `HistoryLimits`; every preparation is independent and only immutable `Sendable` values cross its boundary — confinement is correct; only the hosting filename is misleading.
- **Receipts are `Sendable`-only** (not `Equatable`/`Hashable`) by deliberate spec choice, locked by the symbol snapshot.
- **`ThumbnailService` single-flight does NOT bound concurrent RSS** — it dedups in-flight work per key but does not retain completed bytes, so it does not help the K-concurrent-retained-DTO concern (`concurrent-rss-unbounded`).

## 8. Test-coverage gaps

**One methodological gap, not a handful of unrelated nits:** the suite systematically constructs valid values and force-unwraps; it proves the system works for well-formed inputs but does not pin the **rejection semantics that are the system's PRIMARY safety claim.**

- **`HistoryLimits.init?` rejection branches — ZERO tests.** Only `standard!` (force-unwrap) and five HistoryStorage tests building VALID values are covered. Needed: a parameterized nil-return test for each enumerated rejection (non-positive scalar, range `lowerBound<1`, `userRange` not in `hardMax`, `default` outside `userRange`, `repBytes>captureBytes`, `proposed>totalRevision`) PLUS the missing `repBytes>proposed` pair and the `pageRow`/`thumbnail` inverted-range cases.
- **`HistoryItemID.<` / `RevisionID.<` byte ordering — never directly asserted** (browse/fuzzy determinism depends on it; `RevisionID.<` is otherwise dead).
- **`HistoryItemID.description` (`CustomStringConvertible`) — never asserted**; `RevisionID` lacks `CustomStringConvertible` entirely (spec-mandated asymmetry).
- **WS test helper sorts by `uuidString`, not `HistoryItemID.<`** (`WalkingSkeletonSupport.swift:99`) — coincides today, does not guard the production primitive.
- **Receipts/actions are `Sendable`-only** — tests destructure field-by-field rather than `==`, by deliberate spec choice.

## 9. Notable REFUTED (plausible concerns that are actually correct — for provenance)

- **"A literal `5...1` traps so `init?` cannot return nil."** Confirmed, not
  refuted: run 31449140919 additionally proved inverted `uncheckedBounds`
  traps on Xcode 26.6. The resolution is the finding's endpoint-based
  initializer recommendation, which lets invalid ordering reach `init?` and
  return `nil` without constructing a range first.
- **"`identity-uuid-ordering` is a behavioral regression risk."** Refuted as severity: comparing `uuidString` characters instead of raw bytes is a **no-op for UUIDs** — lexicographic `uuidString` order is provably identical to raw-byte lexicographic order (hyphens at fixed positions; ASCII hex nibble order maps isomorphically to byte order). The test gap is real (`HistoryItemID.<` IS live and never directly asserted) but the function is four lines of trivially-correct code on a rare tie-break path → Nit.
- **"`observe()` untyped `Error` is a Swift-concurrency limitation."** Refuted: `AsyncThrowingStream` is generic over its `Failure` type, so `AsyncThrowingStream<HistoryPage, HistoryFailure>` is legal Swift. The untyped `Error` is a deliberate spec choice (`03a §3`). Reclassified code defect → documentation nit.
- **"The resident DTO is ~256 MiB."** Headline corrected: when `activeRevisionID==nil`, `effectiveContent` returns `canonical.representations.map(\\.content)` and `details()` wraps `representation.content.bytes` directly, so canonical and effective share `Data` buffers via COW → resident ~128 MiB. With an active revision, canonical(≤128)+effective(≤64) = ~192 MiB. The ~384 MiB figure is a **transient decode peak** (item holds canonical + all revisions simultaneously during hydrate), not the resident DTO. This COW sharing is **load-bearing but UNCONTRACTED** — see §10.
- **"100 revisions × 64 MiB."** Self-corrected as impossible: `revisions: [RevisionSummary]` carries only `byteCount: Int` (`DetailDTOs.swift:30`), no bytes — so 100 revisions contribute O(100) small summaries, NOT 100×64 MiB. The 256 MiB `totalRevisionBytesPerItem` cap (not 100×64) bounds the active-revision bytes.

## 10. Open questions / residual risk

1. **Measured vs. analytic read-path memory.** Is there MEASURED read-path heap/RSS evidence (perf runner) at v1's 5,000-item scale that actually hits the ~384 MiB `details()` transient peak, or is the figure purely analytic (derived from the §2 byte caps applied to a maxed-out 100-revision item)? This single answer re-ranks the entire memory cluster: if analytic-only and G8 cannot fire on it, then the read-path findings are deferred-hygiene and the implementation-waste fixes (projector, incremental hydrate) are not worth doing now; if measured, they become the highest-priority work.
2. **HistoryStorage WRITE path is unexamined.** Does the commit kernel (single-writer actor confinement, durable transaction, OCC `ContentVersion`/`ChangePosition` recheck at `§11`, mandatory index update, invalidation publication) carry the same happy-path-tested/rejection-path-untested bias found in HistoryCore, and does it have analogous unbounded-memory or unbounded-time seams on the capture path? The write path is where coherence correctness actually lives and is entirely outside this review.
3. **Is the symbol-surface snapshot actually the cheap gate findings claim?** Would tightening `HistoryLimits.init` to `package`, dropping `Hashable` from byte DTOs, and adding `Equatable` to Receipts each require a one-line `Tests/HistoryCoreTests/SymbolSurface/HistoryCore.symbols.txt` edit or a ripple? This determines whether the surface-hygiene fixes are truly cheap-and-safe or carry hidden cost — and nobody has read the file to confirm.
4. **Uncontracted COW.** The headline "~128 MiB resident not ~256 MiB" depends entirely on canonical/effective sharing underlying `Data` buffers — no spec text or doc-comment guarantees it. A future refactor that copies or mutates a `Data` buffer silently doubles the resident ceiling. The whole memory cluster's best-case figures rest on an invariant nobody wrote down.
