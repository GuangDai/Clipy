## 1. Executive summary

The HistoryDomain module is **architecturally sound and spec-faithful**. Its trust-by-design spine — a pure functional core (`Facts.swift:23-29`) that takes fact completeness as an absolute and emits deterministic mutation plans over immutable Canonical content — is the right spine, and the seven planners honour their side of the contract (D1–D19) under inspection. **The single headline failure is proof, not soundness**: the dedicated per-invariant Domain seam suite does not exist — `Tests/HistoryDomainTests/` contains only `DomainSmokeTests` (6 construction tests), and the only planner seam test anywhere in the tree is `WS9:186` proving D19's `.retainedItems` failure. This is compounded by a certification-honesty contradiction: `PROGRESS.md:81-82` lists the D1–D19 suite as *Delivered* while `roadmap/02-historydomain.md:38` records it as a pending Acceptance-blocker and `V2-roadmap.md:72` explicitly flags the overstatement. Beyond that root cluster, the remaining 31 findings are minor/nit: an unaudited high-leverage HistoryStorage primitive (`SignatureIndex.candidateIDs`), one materially false in-code comment under corruption, one refactor that collapses the entire efficiency cluster (an unconditional eviction sort + triple inventory rebuild per capture), and a perf posture that cannot yet satisfy V2's own J1/P1 admission triggers.

## 5. Efficiency notes

The efficiency cluster is **one refactor, not five findings**. `planCapture`'s per-call cost — a full `O(U log U)` `evictionOrdered` sort (`PlannersCapture.swift:158`) plus a triple `O(N)` inventory rebuild (`.map` at `:138` + `.filter` at `:156` + `.filter` at `:158`) — collapses to a victimCount-first gate: compute `projectedCount`/`unpinnedCount` from raw counts, derive `victimCount = max(userPolicyVictims, hardBoundVictims)` BEFORE any allocation, and only allocate/sort when `victimCount > 0`. The steady-state case (coalesce, or single-victim insert) drops to `O(1)` count arithmetic; `planRetention` gets the same hoist above its `.unchanged` short-circuit. Closing this one fix retires the unconditional-sort, coalesce-rebuild, triple-rebuild, retention-shortcut, and at-cap-unmeasured concerns simultaneously.

Secondary: cache `(exactEquality, extraRepCount)` per confirming candidate during the lane-2 filter pass so `canonicalWinnerRanksBefore` does `O(1)` per comparison instead of re-walking `R` byte-equalities per comparison; introduce a lean `DedupCandidate` fact so the loader never faults `revisionStateBlob` for candidates the planner never reads revisions from; replace lane-1's double-Set build with one Set + membership/count; hoist `Set(incoming.representations)` outside `canonicalContains`'s `.filter`.

Two perf-fidelity nits round out the cluster: `retentionMassEviction` and `clearUnpinned` record an implicit max-of-2 (`median()` on a 2-element array returns `sorted[1]`) rather than `measureMedian`'s 1-warmup-+-5-timed; and the §9 runner's largest capture point (1000 retained) is 5× below the 5000-item hard cap with no at-cap churn workload and no candidate-lane coverage (`C≈0` in every perf workload because distinct-content captures produce no signature matches).

## 6. Security & edge-case notes

- **No crash, no data loss, no false-positive match** was found in any code path. The two data-integrity findings both require silent on-disk corruption of a specific `UInt64` in a signature blob and both yield at worst a *recoverable duplicate* retained item; D7's stated guarantee (never a false byte-confirmed match) is preserved because byte-confirmation always runs (`SignatureBlobCodec.swift:146-149` acknowledges the false-inclusion direction explicitly).
- **The one materially false in-code comment** is `SignatureIndex.swift:104-111` ("without ever dropping a true candidate"). It is load-bearing only because a maintainer could build a fast path on its strength; the corruption that falsifies it is essentially absent in a healthy SwiftData store, so this is a doc-correctness fix, not a soundness hole.
- **Value-layer invariants are enforced by convention at the Storage boundary.** `RetentionPolicy.init` (`Facts.swift:184`) and `PinOrdinal.init` (`State.swift:66`) accept any `Int`; the D19 ≥1 floor is enforced only at `HistoryStorage`. The planner seam is reachable from `@testable` tests (`WS9:186` proves it), and the "fails safe" property is asymmetric: it holds for an unpinned coalesce winner but a `maximumUnpinnedItems=0` + pinned-winner coalesce retires every unpinned item without complaint (a D19 violation in the produced plan, no throw). Decision required: accept as harmless (pinned primary is D13-exempt) or add a `package precondition maximumUnpinnedItems>=1`.
- **Empty-string typeIdentifier, non-validating `EffectiveContent.init`, synthesized `internal` memberwise inits, `DomainRejection.revisionNotFound` dead case** are all either spec-intentional or inert today; documented as nits with doc-comment-only remedies to prevent a future maintainer from "fixing" the wrong layer.

## 7. Concurrency / isolation notes

All seven planners run **synchronously inside `HistoryAuthority`'s non-suspending commit interval** (`HistoryAuthority.swift:152`), so planner CPU serializes every concurrent history operation. This is spec-mandated (`05-authority-kernel.md §5`: no `await` may cross the window in which facts and context are live) and the expensive pasteboard/fingerprint/parsing work is already offloaded to `IngestPreparationActor`/`RevisionPreparationActor`. The correct response is **not** to relocate planning off-actor (blocked by spec §5) but to shrink the inline work via the victimCount-first gate and the candidate-decode slim. The serialized actor at the 5000-item hard cap under sustained paste churn is the one unmeasured concurrency regime — see `perf-cap-blindspot`.

- **`signature-index-false-exclusion-yields-duplicate-item` major framing → minor.** The verdict's MAJOR framing overstated operational risk: the trigger is silent on-disk corruption of one `UInt64` in one blob column (essentially zero absent page/hardware rot in a healthy SwiftData store), the consequence is a recoverable duplicate (no data loss, no crash, no false-positive match), D7's stated guarantee is preserved, and the asymmetry is partly acknowledged in D7's framing. - **Three `planClear-dead-scope-*` re-flaggings → one nit.** All describe `PlannersPinRevision.swift:162` and collapse with the prior cycle's `planclear-ignores-scope-no-switch`. The "latent D12 hazard" framing was overstated each time: the compiler forcing function DOES exist one layer up at `loadClearFacts` (`MutationFactLoaders.swift:264-269` switches exhaustively on scope), so a new `ClearScope` case forces a compile error there; the genuine residue is only that the planner site itself has no fail-closed switch.
