## 1. Executive summary

HistoryStorage is structurally sound and faithful to the Authority-kernel spec across its durable codecs, signature index, ingest preparation, thumbnail single-flight, and `SwiftDataHistory` facade — the per-cycle convergence on `minor`/`nit` for everything except one finding reflects a module whose correctness arguments are mostly correct-by-construction. The single **critical** defect is a real credential-retention leak: `IngestPreparation` step 3 filters `org.nspasteboard.ConcealedType`/`TransientType`/`AutoGeneratedType` *per representation* rather than rejecting the whole capture, so a password carried as `public.utf8-plain-text` alongside a sibling marker is retained, fingerprinted, signature-indexed, and surfaced — exactly the leak the comments at `IngestPreparation.swift:68-72` claim to prevent, and reachable today via the public `ClipboardCapture`/`CapturedRepresentation` inits (not just the unbuilt adapter). The root cause is a flat capture schema (`HistoryCore/Capture.swift:51`) that under-carries pasteboard-level metadata; the leak is a symptom, the schema is the disease. Everything else is hygiene — an unbounded observation recheck loop, a 16 MiB thumbnail bound that is reachable for RGBA/16-bit content and misclassified as an invariant violation, thin unit coverage on a pure value type, dead `StepDeferredError` scaffolding, and several empirically-false "Unreachable" / "cannot hit" comments that carry no regression canary.

## 4. Complexity analysis

| Function / site | Current Big-O (time / space) | Reduction opportunity |
|---|---|---|
| `SignatureIndex.itemIDs` (`:198`) | **O(N) time / O(N) space** per access (fresh `Set(entriesByItem.keys)`, N≤5,000); sole hot caller `FactLoaders.swift:313` once per capture-commit. | Cache a `Set<HistoryItemID>` incrementally maintained in build/apply/markUnready → **O(1)** per access. |

## 5. Efficiency notes

- **Two `lowercased()` allocations per fuzzy-scanned row** (`SearchWorker.swift:710`) — fold the Unicode-alignment guard into Fuse's working copy or cache one lowercased `String`. Hottest path in the module.
- **`currentPosition()` allocates a fresh `ModelContext` per call** (`HistoryAuthority.swift:1524`) to read one scalar; the phase-1 recheck calls it per iteration. Have `firstPage` return `(page, position)` from its single Authority interval to eliminate the extra transient context per requery and narrow the race window.
- **`flights` Task captures up to 64 MiB `sourceBytes`** per distinct-key flight (`ThumbnailService.swift:161`); with the single worker serializing decodes, N-1 queued Tasks each retain their source bytes. Re-fetch `sourceBytes` from the Authority inside the worker so queued Tasks hold zero source bytes (trades one extra Authority hop for bounded memory). Latent.
- **Inlined 16 MiB / 1,024 literals** across four codec test files (`CanonicalBlobCodecTests:92`, `SignatureBlobCodecTests:105`, `EffectiveTypeIdentifiersBlobCodecTests:51`, `RevisionStateBlobCodecTests:135`) — reference `HistoryLimits.standard.maximumEncodedThumbnailBytes` so test constants cannot diverge from production.
- **Two transient O(N) Set allocations per capture-commit** (`itemIDs` + `FactLoaders:330`) — collapse to one cached incremental Set plus a count-equality + subset iteration.

## 6. Security & edge-case notes

- **The critical leak is a security defect, not a perf defect.** A password-manager copy placed on the pasteboard as `public.utf8-plain-text` alongside an `org.nspasteboard.ConcealedType` sibling marker is retained, fingerprinted, indexed, and surfaced. `ClipboardCapture` (`HistoryCore/Capture.swift:51`) carries no pasteboard-level metadata — the marker arrives as "just another sibling representation," forcing the security-critical contract into IngestPreparation step 3 where per-representation filtering is structurally incapable of correctness. The fix MUST be whole-item rejection (or schema change), not a filter tweak. Add proprietary markers (`com.agilebits.onepassword`, `de.petermaurier.TransientPasteboardType`, `com.typeit4me.clipping`).
- **A 2048×2048 incompressible RGBA / 16-bit source** at the max thumbnail extent exceeds the 16 MiB output bound after PNG overhead — the failure surfaces as `.persistence(.invariantViolation)` on valid retained content. Fail-closed (no data corruption), but the classification is wrong and the comments are false.
- **Zero-frame / multi-frame image containers**: `CGImageSourceCreateThumbnailAtIndex` at hardcoded index 0 returns nil for a zero-frame container (maps to `corruptStoredValue`, fail-closed) and returns only frame 0 for animated GIF / multi-page TIFF (cosmetic). Both undocumented.
- **xxh3 cross-version drift** would silently corrupt dedup with no fixture to catch it; durable signatures mean a vendor bump or SIMD-path change on a new deployment target is a latent correctness risk.

## 7. Concurrency / isolation notes

- **The module's safety story is concentrated in one property it does not own**: that `HistoryAuthority`'s plan→transaction→apply (and fact-load) interval contains NO `await`. If that single property ever breaks, four "correct-by-construction" arguments collapse simultaneously — the SignatureIndex generation "agree" check, the validate/apply divergence paths, the "Unreachable" `CanonicalContent` catch, and the phase-1 recheck termination. The module should assert or document this dependency explicitly.
- **`observe()`** correctly registers the invalidation subscriber before the first query and relies on `bufferingNewest(1)` to coalesce bursts in phase-2; the only defect is the unbounded phase-1 recheck (liveness, not correctness). The producer Task DOES capture the facade struct via `self.firstPage` — the comment at line 296 is wrong about that (accurate only for the `onTermination` handler).
- **`IngestPreparationActor` serializes all preparations** by design (single actor, synchronous `prepare`) — bounds peak memory to one in-flight capture; xxh3-64 is GiB/s so 128 MiB is single-digit ms. Off-Authority isolation preserved; off-Authority concurrency not realized. Defensible for v1; document the choice.
- **`ThumbnailService` concurrency is entirely latent** — single worker, unstructured non-cancellable Task, unbounded flights. Zero consumers exist (`PresentationUI/`, `ClipyApp/`). The spec (§9/§14.5) mandates no scroll-rate, concurrency, or cancellation contract. Do not change until a consumer lands.
- **`SwiftDataHistory` actor fields are `internal` not `private`** so the `@testable` harness can install suspension handlers (documented deviation, `PROGRESS.md:248`); cross-module surface unchanged.

- **`prepare()` rejection branches**: none directly exercised (`emptyCapture`, `representationLimit`, `byteLimit` per-rep/total/source-app, `duplicateRepresentationType`, `unsupportedRepresentationType`).
- **`SignatureIndex` pure-value paths**: only `retainedCountExceedsBound` is directly tested. Missing: the other five `SignatureIndexRejection` cases; the four `apply()` divergence→`markUnready` paths (lines 300, 305, 312, 331); the generation-overflow→`markUnready` path; `candidateIDs` edge cases (unready→nil, empty-entries→[], missing-posting→empty intersection, early-break). The pure-value seam makes this cheap.

## 9. Notable REFUTED (plausible concerns that are actually correct)

- **"§16 capacity-vs-invalidInput mismatch" cluster (3 prior "major" findings + the OPEN revision-path twin): NOT a deviation.** Reading `ActorStubs.swift:270-281` directly shows the revision path uses `.capacityExceeded(.revisionCount/.revisionBytes)` for durable capacity AND `.invalidInput(.byteLimit/.representationLimit)` for input size IN THE SAME FUNCTION — the authors demonstrably know the distinction. `Failures.swift:46-47` explicitly reserves `InvalidInputReason.byteLimit` for "A capture exceeded the configured byte limit." Capture/rep/proposed-revision INPUT byte limits are caller-validation, not durable capacity. Downgraded major → nit (spec-wording alignment only). Lesson: read `Failures.swift`'s own docstrings before claiming a vocabulary deviation.
- **"Concealed-type leak is latent only because PasteboardAdapter is a stub": understated.** `Capture.swift:15` and `:56` — both `ClipboardCapture.init` and `CapturedRepresentation.init` are PUBLIC, so any caller (test, library consumer, future adapter) can construct `[utf8-plain-text + ConcealedType]` and trigger the leak TODAY with no adapter. It is latent only under the shipping APP config (no pasteboard source yet), not under the public API. Sharpened the criticality claim (kept critical).
- **"SignatureIndex test gap is major": overstated.** The divergence paths are unreachable end-to-end because the Authority serializes validate→transaction→apply without suspension; a missing test cannot protect against a runtime-observable defect — it guards only against a future programmer-error regression whose blast radius is `markUnready`→rebuild (safe by §11/§13). Corrected major → minor.
- **"16 MiB thumbnail bound" (two prior "major" findings): converged to minor.** The perf-runner's incompressible-noise fixture (RGB color type 2, 1024×1024, requested at `MaxPixelSize=32` per `main.swift:778,816`) does NOT exercise the bound — reachability is RGBA-color-type-6 / 16-bit-specific at exactly the 2048 max dimension, and the failure is thumbnail-only with no data loss. Real defect is the misclassification (`.invariantViolation` on valid content) + the false comments.
- **"Thumbnail concurrency" (two prior "major" findings): real but entirely latent.** Grep of `Sources/PresentationUI/` and `Sources/ClipyApp/` for thumbnail callers returns ZERO matches. §9/§14.5 mandate no scroll-rate, concurrency, or cancellation contract, so no present defect exists. Kept at minor.
- **"Observe busy-loop is major": overstated.** Production capture is NSPasteboard change-count driven (human-paced); `docs/01-architecture.md` §4 confines scripted/sync-replay adapters to SwiftUI previews and forbids them as storage-semantic substitutes, so two commits landing within the milliseconds-wide `firstPage`+`currentPosition` window is essentially impossible. Corrected major → minor; the cheap iteration cap makes it moot regardless.

## 10. Open questions / residual risk

1. **What does `docs/roadmap/04-pasteboardadapter.md` mandate** for `org.nspasteboard.ConcealedType`/`TransientType`/`AutoGeneratedType` — drop-the-whole-item at the source, a pasteboard-level concealed flag on `ClipboardCapture` (schema change), or flatten-as-siblings (current, leaking)? This single answer resolves the critical finding's fix location and unblocks Cluster A.
2. **Does HistoryAuthority's plan→transaction→apply (and fact-load) interval contain ANY `await`?** If yes, the SignatureIndex generation "agree" check becomes a real correctness obligation, the validate/apply divergence becomes runtime-reachable, and the "Unreachable" `CanonicalContent` catch can fire on interleaves — four findings flip from moot-and-document to real-bug. If no, the entire generation/test-gap cluster is confirmed correct-by-construction.
3. **Does v1 ship a multi-image grid UI or only single-item preview?** This decides whether the entire thumbnail-concurrency cluster (single-worker serialization, non-cancellation, unbounded flight retention) is a real efficiency defect or an accepted simplification — and whether §9/§14.5 must pin a scroll-rate/cancellation/cardinality contract.
4. **Is the vendored xxh3 byte-stable** across the pinned version AND all macOS deployment targets (SIMD-path independence), and is there a fixture pinning a known byte-vector → known `UInt64`? A yes-with-fixture closes the cross-restart dedup-drift risk; a no elevates it from minor.
5. **Should §16's "hard representation/byte/revision/copy-count limits → `.capacityExceeded`" bullet be reworded** to split capture-input size (→ `.invalidInput`, current code) from retained/revision durable capacity (→ `.capacityExceeded`, current code), or does the code need new `CapacityKind` cases? Resolves the residual vocabulary nit and prevents re-flagging the phantom deviation.
